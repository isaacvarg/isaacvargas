## The Problem

Under FDA MoCRA (Modernization of Cosmetics Regulation Act) requirements, cosmetic manufacturers must register every product's ingredient list through the FDA's Cosmetics Direct portal. The problem is that the portal doesn't accept the industry-standard INCI (International Nomenclature Cosmetic Ingredient) names that appear on product labels. Instead, it requires each ingredient's UNII (Unique Ingredient Identifier) code and FDA's preferred substance name. For a product with 30+ ingredients, manually cross-referencing each one against FDA databases is tedious, error prone, and a real bottleneck during registration season.

## The Solution

INCI-to-UNII is a web application that automates the entire conversion pipeline. A user pastes a comma-separated INCI listing, exactly as it appears on a product label, and the app resolves each ingredient to its UNII code and preferred name via the FDA's public API in real time. The results are displayed in order of predominance (preserving the regulatory ordering from the label) and can be exported as a CSV file formatted to the Cosmetics Direct portal's exact import schema.

## Key Technical Decisions

### FDA API Integration

Not every INCI name maps cleanly to a UNII entry. Trade names, regional naming variations, and multi-component ingredients can all cause misses with the API. Rather than forcing the user to leave the app and hunt through PrecisionFDA manually, unresolved ingredients are flagged inline (highlighted in red) and a blank row is preserved in the CSV export so the order of predominance stays intact. So rather than blocking the entire workflow on a lookup failire, partial results with clear error signaling allow the user to contiue without stopping.

### Persistent Custom Mappings

The app includes a custom-mapping feature backed by Prisma and SQLite. When a user manually resolves an ingredient the FDA API couldn't match, that mapping is persisted and applied automatically on all future conversions. Over time, the system builds an organization-specific dictionary that fills the gaps in the public API which allows it to learning the edge cases of each company's ingredient catalog.

### Export-Ready Output

The CSV export isn't just a data dump. It's structured to match the Cosmetics Direct portal's expected import format: preferred ingredient name, UNII code, and a direct link to the PrecisionFDA entry for each ingredient. The goal was zero friction between conversion and submission: no reformatting, no copy-pasting columns, no manual cleanup.

## What I Learned

This project sat at the intersection of software engineering and regulatory compliance.  Building it taught me to treat regulatory schemas as first-class API contracts: the CSV export format, the field ordering, the handling of null entries all had to conform to an external system's expectations with no room for "close enough." It also reinforced the value of progressive enhancement in developer tools. The custom-mapping system started as a workaround for API gaps but became the feature users relied on most, because real-world ingredient data is messier than any public database accounts for. This project also help me see how much time could be saved by having software handle the heavy lifting with a chemist verifying and using the data. The has inspired me to make many other tools to help the regulatory strain, such as IFRA percentage calculators and Safety Data Sheet parsers.

## Future Considerations

This was a huge time saver for my colleagues and a valuable tool once our nuanced material dictionary was filled up to cover for the gaps in the public API. I would love to elaborate on this probject and create software that aggregates many tools for chemist and formulators. Such a software would include a registry of materials that would store details such as chemical IUPAC nonemclature, genus and species names for botanicals, aliases, regional names, regulatory status by country, and more. Each of the details would be modifiable by users and verified by a moderators; when submissions the users would submit scientific basis for the change and upload supporting documents for moderators to review. 

With such a software, the gaps in public APIs could be crowdsourced so all chemist could benefit from the data rather than expanding a self-hosted dictionary. Then this data could help chemist with much more regulatory preparation than just MoCRA registration.
